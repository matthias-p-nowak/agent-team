# Runner architecture

`runner.py` runs from a task working directory separate from its own installation. It copies missing default Markdown prompts from `prompts/`, discovers eligible Pi models before each leader call, and alternates the retained leader with selected workers until a stop or failure. Prompt instructions delegate feature tracking and development decisions to the leader; the runner validates the handover and records file changes and missed updates.

The runner stores settings, disqualifications and evaluation events atomically in `runner.json`, appends diagnostics to `runner.log`, and uses a PID lock to prevent concurrent runs in one directory. Pi subprocesses run in separate process groups with streaming JSON output, per-call timeouts and an invocation deadline. Failed llama.cpp loads trigger model removal; `--remove` also attempts removal of existing disqualifications. See [design](design.md) for the behavior and edge cases.

Diagnostics: the raw `next.txt` content and the concrete rejection reason are logged and used as the leader's disqualification reason. Only tool starts and failed tool ends are shown and logged (`tool_execution_update` and successful ends are ignored). `run_pi()` remembers each start's target by `toolCallId` so a failed end can name it; `result_text()` extracts the text blocks of the tool result. Each streamed call ends with a newline. An empty or unreadable `runner.lock` is treated as stale. SIGTERM/SIGHUP handlers raise an `Interrupted` exception so the same cleanup path as Ctrl+C terminates the Pi process group and releases the lock. `team.txt` keeps Pi's header row and prefixes each row with a hash id (`model_ids()`); `discover()` returns an id → (provider, model) map, and `handover()` resolves the 2-line handover via `parse_id()`. `run_pi()` also returns the number of tool calls; a worker call with none and an unchanged `report.md` is treated as a failure ("did no work"). Leader and worker calls go through `call_model()`: on "is not running" it calls `load_model()` (`POST /models/load`, then `model_status()` polls `GET /models` up to `LOAD_WAIT` = 600 s) and retries once; `load_failure()` decides removal.
